## 1.一分钟讲清项目

### 1.1 一句话定位

这是一个不解密业务内容、只利用流量统计特征与 TLS/连接日志语义来识别 8 类加密网络流量的实验系统：先用 DeBERTa 提取日志语义特征，再用监督对比自编码器降维，与 80 维手工流量特征融合，最后用 LightGBM 分类，并通过 FastAPI 和静态前端展示结果。

### 1.2 30 秒面试版

项目解决的是“流量加密以后，载荷不可读，怎样识别恶意行为”的问题。输入是 PCAP/PCAPNG，系统按双向五元组近似组织流，截取每条流前 200 个包，提取 80 维统计与时序特征，并生成紧凑的连接、TLS 和证书日志文本。日志文本经过 DeBERTa-v3 的替换词检测预训练和 LoRA 分类微调，得到 768 维 `[CLS]` 表征；再通过 SupCon-AE 压缩到 64 维，与 80 维手工特征拼成 144 维，交给 LightGBM 做八分类。项目还提供训练评估、结果可视化、SSE 进度推送和 Web 演示界面。

### 1.3  两分钟展开版

项目的核心动机是：加密流量不能依赖明文关键词，但通信行为仍会在包长、方向、时间间隔、握手特征、证书字段和连接上下文中留下痕迹。因此系统采用两条特征分支。

第一条是手工特征分支。项目使用纯 Python 解析 PCAP/PCAPNG，支持 IPv4 下的 TCP/UDP，将正反方向归并为一条流，在线计算包数、字节数、包长分布、IAT、TCP 标志、活跃/空闲周期和 60 秒邻域上下文等 80 维数值特征。第二条是语义分支。连接、SSL、X509 风格记录被压缩成短 JSON 文本，DeBERTa-v3 先进行 ELECTRA 风格的 RTD 领域预训练，再用 LoRA 做八分类监督适配，最后取编码器最后一层的 `[CLS]` 向量。

直接拼接 768 维语义特征与 80 维手工特征会让维度严重失衡，所以当前主方案用监督对比自编码器将语义特征压到 64 维。它同时优化重构损失和监督对比损失，使同类样本更近、异类样本更远。最终 144 维特征送入 LightGBM，使用类别平衡权重完成八分类。

工程上，项目用 FastAPI 提供任务、预测、评估和元数据接口，用 SSE 推送流水线进度，SQLite 保存任务状态，前端展示上传、TLS 分析、检测和告警页面。用户上传不要求文件名携带标签，只执行 `mff_lightgbm.inference` 并加载冻结的 `checkpoints/production/v1`；离线训练与在线推理已经隔离。当前系统仍属于研究验证系统，因为旧版特征解析和随机流级数据划分尚不能证明跨抓包泛化能力。

## 2. 项目目标、类别和边界

### 2.1 目标

输入网络抓包，判断每条流属于以下 8 类之一：

| ID | 类别 | 含义 |
|---:|---|---|
| 0 | benign | 正常流量 |
| 1 | adware | 广告软件流量 |
| 2 | dns2tcp | DNS 隧道工具 dns2tcp |
| 3 | dnscat2 | DNS 隧道工具 dnscat2 |
| 4 | iodine | DNS 隧道工具 iodine |
| 5 | ransomware | 勒索软件流量 |
| 6 | scareware | 恐吓软件流量 |
| 7 | smsmalware | 短信恶意软件流量 |

### 2.2 项目不做什么

- 不解密 TLS 载荷，也不恢复用户明文。
- 不进行 DPI 意义上的完整协议重组。
- 不实现完整 Zeek，也没有完整解析 X.509 ASN.1。
- 当前不支持真正的开放集未知类别识别。
- Web“真实检测”只运行单 PCAP 特征提取、语义编码、固定 SupCon-AE 变换和固定 LightGBM 推理，不进行训练。
- 当前结果不能直接表述为“可泛化到任意新网络环境”。

### 2.3 “LLM”这个名称应怎样解释

源码中的语义表征代码现位于 `src/mff_lightgbm/representation` 与 `training`。核心模型是 DeBERTa-v3-base 编码器，不是生成式大语言模型。面试时更准确的说法是“预训练语言模型/Transformer 语义编码器”。它把结构化日志序列当作文本建模，输出判别式表示，不负责生成回答。

## 3. 总体架构与端到端数据流

```text
PCAP / PCAPNG
    │
    ├─ 1. 按双向流截断：每流最多保留前 200 包
    │      src/mff_lightgbm/data/truncate_pcap.py
    │
    ├─ 2. 流解析与统计
    │      ├─ 80 维手工数值特征
    │      ├─ conn / ssl / x509 风格日志
    │      └─ temporal 包级时序 CSV
    │      src/mff_lightgbm/data/extract_flow_features.py
    │
    ├─ 3. 日志紧凑序列化为 JSONL
    │      src/mff_lightgbm/data/preprocess.py
    │
    ├─ 4. DeBERTa-v3 语义分支
    │      ├─ RTD 领域预训练
    │      ├─ LoRA 八分类适配
    │      └─ 提取 768 维 [CLS]
    │
    ├─ 5. SupCon-AE：768 → 64
    │
    ├─ 6. 融合：64 维语义 + 80 维手工 = 144 维
    │
    ├─ 7. LightGBM 八分类
    │
    └─ 8. CSV / 报告 / 混淆矩阵 / ROC / 风险资产 / Web 页面
```

开发者离线入口是 `mff-offline`。默认 `--stage all` 执行：

```text
truncate → flow_features → preprocess_feature → extract → detector
```

它没有单独调用 `supcon` 阶段，因为 `detector` 内部会基于训练集重新训练 SupCon-AE，再变换全部样本。独立 `supcon` 阶段主要用于加载已有降维器并单独产出降维 CSV。

### 3.1 三条需要区分的数据链

1. DeBERTa 预训练/LoRA 数据：由训练流特征 CSV 切分生成 JSONL。
2. 语义特征提取数据：当前主要来自测试流特征 CSV。
3. 最终 LightGBM 数据：在已提取语义特征的数据上，再做一次 70%/10%/20% 的随机分层划分。

这意味着“上游训练/测试文件分开”不等于“最终评估是完全独立的新抓包评估”。最终分类器会在所谓测试抓包中的流上重新训练和随机评估。

## 5. 数据处理与 80 维手工特征

### 5.1 抓包截断

`truncate_pcap.py` 用纯 Python 读取经典 PCAP 和 PCAPNG，把正反方向端点规范化为同一流，仅保留每条流最早的 200 个包，再统一写成 little-endian PCAP。

这样做的目的：

- 限制超长流的计算成本和类别偏置；
- 让不同流的观察窗口更一致；
- 对强调握手和连接初期行为的任务较合适。

当前边界：

- 主要支持 IPv4 TCP/UDP，不覆盖 IPv6。
- 链路层偏移通过若干固定位置尝试，不是完整链路层解码器。
- 截断流键实际只含源/目的 IP 和端口，未包含传输层协议；极端情况下 TCP/UDP 相同端点可能碰撞。
- PCAPNG Simple Packet Block 没有原始时间戳时，代码用当前时间替代，时序真实性会损失。
- 只扫描指定目录顶层文件，不递归。

### 5.2 双向流组织

特征提取器先查正向键，再查反向键；第一次出现的方向被定义为 forward。每个流累计：

- 正向/反向包数和字节数；
- 包长分布；
- 到达间隔 IAT；
- TCP 标志计数；
- 活跃与空闲周期；
- 包级方向、长度和相对时间；
- 连接前后一定窗口内的邻域行为。

这里的“方向”是抓包中首次观察到的相对方向，不一定严格等于业务客户端到服务端。

### 5.3 在线统计

包长、IAT 等统计量使用 Welford 在线算法更新均值与方差。它相比“保存全部数值后计算”有两个优点：

1. 单次扫描即可更新；
2. 数值稳定性优于直接用 `E[x²]-E[x]²`。

核心更新关系：

```text
n ← n + 1
δ  = x - mean
mean ← mean + δ / n
M2 ← M2 + δ × (x - mean)
variance = M2 / (n - 1)
```

不过当前实现仍会保留较多流和时序对象，因为跟踪数量和内存限制被设为无穷/空，面对大型抓包仍可能占用大量内存。

### 5.4 80 维特征可以怎样归类

面试时不必死背每个列名，更重要的是讲清这些特征族：

| 特征族 | 代表信息 | 为什么有用 |
|---|---|---|
| 基本连接 | 协议、持续时间、端口 | 区分服务和会话形态 |
| 流量规模 | 双向包数、字节数、比率 | 反映上传/下载和隧道行为 |
| 包长统计 | min/max/mean/std/分位数 | 加密后仍保留尺寸模式 |
| 时间统计 | IAT、持续时间、活跃/空闲 | 反映自动化、心跳和突发行为 |
| TCP 状态 | SYN/ACK/FIN/RST 等 | 反映握手失败、扫描和异常断开 |
| 双向关系 | 前后向比例、首包方向 | 反映客户端/服务端交互结构 |
| 60 秒上下文 | 重连、失败率、唯一目的地 | 单流之外识别主机行为 |
| 衰减统计 | 时间衰减计数/持续时间 | 强调临近事件而弱化旧事件 |

### 5.5 60 秒上下文特征

所有流按时间排序，通过二分定位每条流附近 60 秒范围，再计算重置率、失败率、重连次数、唯一目的地、源地址异常比例、持续时间分位数和指数衰减统计。

价值在于：恶意行为往往不是单条流异常，而是短时间内重复连接、探测多个目的地或高失败率。代价是需要先收集并排序大量流，严格流式处理较困难。

### 5.6 TLS/X509 日志的真实边界

这是面试中必须准确表达的一点。当前代码生成的是“Zeek 风格”的派生记录，不是调用 Zeek 得到的完整日志：

- 从 443 端口 TCP 载荷中用正则启发式寻找 CN；
- 对找到的 CN 生成 SHA-256 指纹；
- issuer、序列号、有效期、密钥长度、签名算法等字段包含合成值；
- TLS 版本和 cipher 也有固定/占位设置；
- 没有完整解析 TLS ClientHello/ServerHello 和 X.509 ASN.1。

因此正确说法是：“项目构造了适合语义编码的连接/TLS/证书风格日志原型。”不能说“系统已经精准解析真实证书链和全部 TLS 握手字段”。若要生产化，应接入 Zeek、tshark、Scapy 扩展或专门 TLS/X.509 解析库，并保留字段可信度标记。

### 5.7 文件和标签规则

类别由文件名 `_sampled_` 前缀推导；训练/测试主要依据 `_train.pcap` 和其他后缀区分。当前代码对 `.pcapng` 的收集和最终 train/test 判断不完全一致：`*_train.pcapng` 可能被错误路由到测试集合。这是一个明确的后缀判断缺陷。

数据源字段根据文件名是否含 `cooked` 推断为 DoH2020 或 CIC2017。这是命名约定，不是从抓包元数据自动识别。

## 6. 日志预处理、DeBERTa RTD 与 LoRA

### 6.1 CSV 到 JSONL

`preprocess.py` 对每条流执行：

1. 校验 80 个数值列是否齐全；
2. 用 `ast.literal_eval` 兼容解析 CSV 中的字典/列表字符串；
3. 把连接、SSL、X509 字段压缩为 `c/s/x` 等短键，减少 token；
4. 生成一行 JSONL，包含 `flow_uid`、地址、紧凑文本、标签、事件数和 `num_features`。

`flow_uid` 缺失时，会由端点和时间戳等信息构造规范 ID。IP、文件名等标识字段用于关联和展示，不进入最终模型特征。

### 6.2 为什么日志适合 Transformer

日志虽然是结构化数据，但字段之间存在上下文关系，例如连接状态、TLS 版本、证书主体和目的端口共同出现时才有意义。Transformer 可以通过自注意力学习跨字段关系。字段压缩则能在 256/512 token 上限内保留更多事件。

### 6.3 RTD 领域预训练

项目采用 ELECTRA 风格 Replaced Token Detection：

1. 随机选择约 15% 的非特殊 token；
2. 6 层 generator 预测被遮盖 token，并从分布采样替换词；
3. 12 层 DeBERTa discriminator 判断每个有效位置是否被替换；
4. 联合优化生成器 MLM 损失和判别器二分类损失。

```text
L_total = L_generator + 50 × L_discriminator
```

RTD 的优势是几乎每个 token 都给判别器贡献训练信号，比只在 mask 位置计算损失更样本高效。DeBERTa 的解耦注意力分别建模内容与相对位置，也适合字段顺序和字段内容同时重要的日志序列。

实现细节：

- 至少保证每个 batch 样本有一个 mask；
- 特殊 token 和 padding 不参加替换判别；
- discriminator 正标签只标记“被选中且实际替换成不同 token”的位置；
- 使用 AdamW、线性 warmup、梯度裁剪和有限值检查；
- 模型以 float32 训练。

当前限制：预训练没有独立验证集，所谓 best checkpoint 和 early stopping 依据训练平均损失。因此它只能说明训练目标继续下降，不能证明泛化最优。

### 6.4 LoRA 八分类适配

领域预训练后，代码加载最新预训练 checkpoint，用 `AutoModelForSequenceClassification` 建立 8 类分类器，并对注意力中的 query、key、value 投影加入 LoRA：

```text
W' = W + (α/r) × B × A
```

其中 rank `r=8`、`alpha=16`、dropout `0.1`。主干权重基本冻结，只训练低秩矩阵和分类头/池化层，优点是：

- 训练参数和显存更少；
- 降低小数据上全量微调的过拟合风险；
- adapter 文件只有数 MB，便于版本化。

训练采用 batch size 2、梯度累积 8，按验证集 macro-F1 选最优，准确率作为同分条件。

当前缺陷：训练结束后的最终测试直接评估当前模型，没有重新加载已经保存的最佳 adapter。因此最终报告可能对应最后一轮，而非验证 macro-F1 最优轮。修复方式是测试前显式重载 `best` checkpoint。

### 6.5 数据集实现的内存取舍

`dataset.py` 和特征提取数据集会提前把全部文本 tokenize 并堆叠成固定长度 tensor。这让训练迭代简单，但数据量大时内存占用高。更可扩展的做法是惰性 tokenize、动态 padding、Arrow/Datasets 映射缓存或 IterableDataset。

### 6.6 为什么先做分类微调再提特征

仅做 RTD 的表示偏向“日志语言结构”；加入八分类 LoRA 后，表示会向任务相关边界靠拢。最终不是使用分类概率，而是取最后隐藏层 `[CLS]` 的 768 维向量，给下游降维和树模型使用。这是一种“深层表示学习 + 传统分类器”的混合方案。

## 7. 语义降维与多维特征融合

### 7.1 为什么不能直接 768 + 80

直接拼接得到 848 维时，语义特征数量远大于手工特征。LightGBM 使用 feature fraction 等随机特征选择时，语义维度更容易占据多数候选；同时 768 维中可能存在冗余和噪声。降维既控制计算量，也让两条分支更平衡。

### 7.2 SupCon-AE 结构

当前主方案是监督对比自编码器：

```text
Encoder: 768 → 256 → 128 → 64
Decoder: 64 → 128 → 256 → 768
Projector: 64 → 64
```

网络包含 LayerNorm、ReLU 和 dropout。总损失为：

```text
L = L_reconstruction + L_supervised_contrastive
```

- 重构损失确保 64 维瓶颈保留原始语义信息；
- 监督对比损失让同标签样本靠近、不同标签样本分开；
- 温度系数为 0.1；
- WeightedRandomSampler 缓解类别不平衡；
- 输入先用只在训练集拟合的 StandardScaler 标准化。

### 7.3 对比学习如何工作

对 anchor `i`，同类样本集合是正样本，其他类别是负样本。目标大意是提高 anchor 与正样本的相似度，并压低与所有其他样本的相似度：

```text
L_i = -平均 log[ exp(sim(i,p)/τ) / Σ exp(sim(i,a)/τ) ]
```

实现对“一个 batch 中没有同类正样本”的情况做了保护，也对相似度计算做了数值稳定处理。

### 7.4 防止降维器泄漏

当前 `detector.py` 先划分 train/val/test，再只用 train 和 val 训练 SupCon-AE，最后变换全部集合。StandardScaler 也只拟合训练语义特征。这比“先在全部数据降维再划分”更正确，因为测试标签和测试分布不会参与降维器训练。

checkpoint 保存网络权重、标准化统计、特征顺序、类别和最佳 epoch。加载时会严格验证 768 个语义列顺序，并拒绝旧格式，降低错列后静默产生错误结果的风险。

### 7.5 PCA 备选方案

`pca_reduce_features.py` 提供无监督线性基线：只把 `feat_*` 降至最多 64 维，80 维手工特征保持不变。PCA 简单稳定、训练快，但只最大化方差，未利用类别标签，也不能表达非线性流形。

### 7.6 最终特征

```text
64 维 SupCon-AE 语义特征
+ 80 维手工统计特征
= 144 维融合特征
```

## 8. LightGBM、评估结果与结果解读

### 8.1 训练流程

`detector.py` 的核心流程：

1. 规范化字符串/整数标签；
2. 删除 UID、IP、协议、来源、文件名、原始日志等非模型字段；
3. 对低基数对象列编码，高基数对象列丢弃；
4. 随机分层切分约 70% train、10% validation、20% test；
5. 训练 SupCon-AE 并得到 144 维特征；
6. 根据类别频次计算平衡样本权重；
7. 训练 LightGBM multiclass，并在验证集 early stopping；
8. 在测试集输出分类报告、混淆矩阵、概率、ROC、风险资产和可视化。

主要参数：63 leaves、学习率 0.03、feature/bagging fraction 0.8、叶节点最小样本 50、L1/L2 均为 0.1、最多 2000 轮、100 轮 early stopping。

为什么选择 LightGBM：

- 对统计特征和深层表示混合的表格数据很强；
- 能表达非线性和特征交互；
- 不要求所有特征同尺度；
- 训练、推理和特征重要性分析成本适中。

### 8.5 其他评估细节

- 数值缺失值的中位数在完整 dataframe 上计算，理论上存在轻微预处理泄漏；应只在训练集拟合并复用。
- 低基数类别编码也应在训练集拟合并处理未知值。
- 风险资产默认把“预测为恶意且最大概率 ≥ 0.8”的流列为高置信告警；这个阈值未经独立校准。
- Micro-AUC 容易受多数类影响，应同时看 macro-AUC、PR-AUC、每类召回率和误报率。
- 当前资源 benchmark 报告中手工阶段被跳过、detector 因缺少 LightGBM 失败，总耗时为 0；它不是有效的性能基准。
- benchmark 的 RSS 只取阶段开始与结束值的较大者，不是真正的运行时峰值，而且不完整统计子进程资源。

## 12. 高频算法与网络面试问答

### Q1：加密以后为什么还能分类？

加密隐藏了应用载荷内容，但不会完全隐藏包长、方向、到达时间、连接持续时间、端口、握手行为和通信上下文。不同程序的协议实现与业务流程仍会形成统计指纹。项目同时使用行为统计和可观察日志元数据，但不会声称它能读出明文。

### Q2：为什么按双向流，而不是单向五元组？

攻击和正常会话都包含请求与响应关系。合并正反向可以计算上下行比例、方向性 IAT 和握手状态。实现中第一包决定 forward，需要意识到中途抓包时方向可能不等于真实客户端方向。

### Q3：为什么只取前 200 个包？

控制计算与存储，减少长流支配，并重点捕捉握手和早期行为。代价是可能错过后期恶意行为，应该通过不同截断长度的消融确认。

### Q4：Welford 比直接方差公式好在哪里？

它单遍、低内存且数值稳定，避免两个大数相减造成浮点误差，适合流式包统计。

### Q5：RTD 与 BERT MLM 有什么区别？

MLM 只预测被 mask 的少数位置；RTD 先由 generator 替换 token，再让 discriminator 判断每个位置真假，更多 token 提供监督信号，因此样本效率通常更高。

### Q6：为什么用 DeBERTa？

它将 token 内容和相对位置分开建模，适合字段内容与顺序都重要的日志；已有预训练权重也能提供良好初始化。但是否优于更小模型必须通过同等预算实验验证。

### Q7：为什么还要 LoRA？

领域数据有限，全量微调成本和过拟合风险较高。LoRA 用低秩增量适配注意力层，训练参数少、checkpoint 小，同时让表示对八分类任务更敏感。

### Q8：为什么不直接用 Transformer 分类头？

项目希望融合数值流量特征，而树模型对异构表格特征和非线性交互更自然。Transformer 负责语义表示，LightGBM 负责最终融合分类。不过必须通过消融确认这种复杂链条值得；当前结果反而显示手工特征更强。

### Q9：SupCon-AE 为什么同时需要重构和监督对比？

只重构可能保留与分类无关的方差；只对比可能丢失大量语义结构并过度贴合标签。联合目标在信息保留与类别可分性之间折中。

### Q10：为什么 SupCon batch 需要同类样本？

监督对比损失需要正样本对。类别不平衡或 batch 太小时可能没有同类样本，因此实现用了 WeightedRandomSampler，并对无正样本情况做保护。

### Q11：为什么选 macro-F1？

八类样本不均衡，accuracy 和 weighted-F1 容易被 benign 主导。macro-F1 让每类等权，更能暴露少数恶意类别召回不足。

### Q12：为什么 AUC 很高但准确率不是同样高？

AUC 衡量不同阈值下的排序能力，不等于固定 argmax 决策的正确率；micro-AUC 还受多数类影响。类别概率可能有良好排序但校准或类别边界仍不理想。

### Q13：什么是数据泄漏？本项目哪里最危险？

任何测试集信息进入训练、预处理或模型选择都属于泄漏风险。最大问题是同一抓包的流同时出现在 train/val/test，模型可能识别采集环境而非通用恶意行为。其次是全量数据中位数填充和类别编码。

### Q14：为什么随机分层切分不够？

分层只保证类别比例，不保证独立采集单元隔离。网络流高度相关，同一 PCAP 中的主机、时间和环境特征重复，必须按 PCAP/主机/时间 group 切分。

### Q15：当前系统能识别未知恶意流量吗？

不能严格做到。Softmax 八分类必然把输入归到已知类，Web 也拒绝 real_unknown。需要 OOD 分数、阈值校准、未知类数据和独立开放集评估。

### Q16：LightGBM 为什么适合？

它适合中等规模表格数据，能建模非线性和高阶交互，训练快、无需复杂尺度处理，并能输出特征重要性。但高维噪声仍会伤害它，这也是降维和消融的原因。

### Q17：如何处理类别不平衡？

SupCon 阶段使用加权采样，LightGBM 使用类别平衡样本权重，评估看 macro-F1 和每类召回。还可以尝试 focal loss、阈值移动或按运营成本定义代价矩阵。

### Q18：如果手工特征最好，为什么保留语义分支？

当前证据下应该把手工特征作为主基线和候选上线方案。保留语义分支是研究方向，不应包装成已验证收益。它可能在真实 TLS 字段、更丰富跨环境数据或后期融合下提供泛化增益，需要新实验验证。

## 13. 高频工程面试问答

### Q1：为什么用 SSE，不用 WebSocket？

任务进度主要是服务端到客户端的单向事件流，SSE 基于 HTTP、浏览器原生重连、实现简单。若需要双向交互、高频控制或二进制通信，再考虑 WebSocket。

### Q2：当前 SSE 有什么问题？

事件队列只在单进程内存中，任务结束即删除，不能可靠重放；多 worker 不共享。生产可使用 Redis Streams/PubSub、持久事件表和 Last-Event-ID。

### Q3：如何可靠取消外部训练进程？

Orchestrator 需要持有子进程句柄，取消时先发终止信号，等待宽限期，再强制杀死进程树；finally 中关闭管道并更新数据库。只取消 asyncio task 不够。

### Q4：为什么真实任务需要锁？

当前任务共享 raw 目录和固定输出路径，并发会互相覆盖，所以用锁串行化。但根本解决方案是任务目录隔离与只读模型 bundle，而不是依赖全局锁。

### Q5：怎样把系统改成生产推理服务？

离线完成训练并注册不可变模型 bundle；在线上传后只做截断、特征 transform、语义编码、reducer transform 和 LightGBM predict；结果按 task ID 存储，配合队列 worker、限流、鉴权、监控和超时。

### Q6：为什么 SQLite 只适合当前规模？

单机低并发任务状态足够简单，SQLite 零运维。但多实例写入、任务队列、事件订阅和复杂查询更适合 PostgreSQL + Redis/消息队列。

### Q7：怎样防止上传漏洞？

生成服务端文件名而非信任客户端名称；限制扩展名、魔数、大小、数量和处理时间；使用独立目录；禁止路径分隔符；最低权限运行；扫描压缩炸弹/损坏格式；设置磁盘配额和定期清理。

### Q8：缓存为什么会脏？

DataProvider 缓存 dataframe，但流水线原地覆盖源 CSV，缓存没有基于 mtime/hash 失效。解决方案是不可变版本路径，或在文件版本变化时原子替换并清缓存。

### Q9：如何避免新模型上线后特征错位？

把特征名和顺序写进模型元数据，推理时严格校验；SupCon checkpoint 已做这件事。还应对手工特征 schema、类别映射、tokenizer 和 LightGBM feature names 做同样校验。

### Q10：怎样做可观测性？

记录每阶段耗时、吞吐、输入输出行数、失败原因、CPU/RSS/GPU、队列等待时间、模型版本、数据版本、预测分布和漂移；用 task ID 串联结构化日志和 trace。

```text
                └─ compact logs → DeBERTa 768 → SupCon-AE 64┘
```

讲解顺序：输入边界 → 两条分支 → 为什么降维 → 为什么树模型 → 输出和指标 → 消融结果。

### 16.2 正确的生产训练/推理边界

```text
Offline training:
versioned data → group split → fit encoder/reducer/LightGBM → immutable model bundle

Online inference:
one task PCAP → task-local features → frozen transforms → predict → task-local result
```

然后指出当前实现将这两个边界混在一起，这是你下一步工程化改造的重点。

## 17. 最后的项目判断

这个项目的强项不是某一个模型，而是完整覆盖了抓包解析、特征工程、Transformer 表示、监督降维、树模型、评估和 Web 任务系统，适合展示跨网络安全、机器学习和工程实现的综合能力。

它当前最需要补强的也不是继续叠加模型，而是实验有效性和训练/推理边界：补充每类多个独立抓包、按 group 做严格评估、把 TLS 字段变成真实解析数据、修复并重跑消融，然后把 Web 改成加载冻结模型的任务隔离推理服务。

面试中的最佳姿态是：清楚讲出为什么这样设计，也能用代码和数据指出设计哪里尚未成立。尤其要主动说明“手工特征目前更强”和“同抓包随机切分可能高估泛化”——这不会削弱项目，反而证明你理解实验，而不只是复述指标。
